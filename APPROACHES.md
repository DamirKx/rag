# Подходы к реализации RAG-системы для нормативно-правовых документов

**Тема:** Разработка вопросно-ответной системы на базе RAG-архитектуры для анализа нормативно-правовой документации.

**Ограничение (уточнено):**
- **Запрещено:** готовые решения «как есть» — облачные API (ChatGPT, Gemini, GigaChat, YandexGPT), а также любые модели, которые используются без дообучения (zero-shot, готовые эмбеддеры без обучения).
- **Разрешено:** предобученные модели-основы, которые **дообучаются (fine-tuning)** на собственных данных, а также модели, обученные с нуля.
- Допустимые библиотеки: `numpy`, `scipy`, `PyTorch`, `transformers` (как инструмент загрузки базового чекпоинта и обучения), `scikit-learn`.

> Принцип защиты работы: для каждого компонента есть **baseline** (классический алгоритм или модель без дообучения — только как точка сравнения в эксперименте, не как часть системы) и **итоговая версия** (дообученная или собственная). Это даёт таблицы «до / после».

### Два трека реализации

В документе описаны оба пути. Их можно комбинировать: например, поиск — собственный BM25 + дообученный эмбеддер.

| Трек | Суть | Когда выбирать |
|---|---|---|
| **A. С нуля** | Классические алгоритмы и малые нейросети, обученные с нуля (разделы 3–6) | Мало данных/вычислений, нужен максимум «своего кода» |
| **B. Fine-tuning** | Предобученная база + дообучение на своих данных (раздел ниже) | **Основной рекомендуемый путь:** лучшее качество, стандартная методика |

### Трек B: что дообучать

| Компонент | Базовые модели для дообучения | Метод дообучения | Данные |
|---|---|---|---|
| **Эмбеддинги (retriever)** | `ruBERT-base`, `multilingual-e5-small/base`, `ru-en-RoSBERTa`, `LaBSE`, `paraphrase-multilingual-MiniLM` (текущая модель в проекте) | Контрастное обучение: `MultipleNegativesRankingLoss`, hard negatives, адаптация домена через TSDAE/GPL | Пары «вопрос → статья» (раздел 2.2) |
| **Реранкер** | cross-encoder на базе `ruBERT` / `xlm-roberta-base` | Бинарная/pairwise классификация релевантности | Пары с hard negatives из BM25 и dense |
| **Extractive QA** | `ruBERT` + голова span-prediction | Дообучение на «вопрос + статья → отрезок ответа» | Размеченные ответы (можно полуавтоматически) |
| **Генератор ответа** | `ruT5-base`, `FRED-T5`, `ruGPT-3 small`, `Qwen2.5-0.5B/1.5B` | Seq2seq fine-tuning или **LoRA/QLoRA** для декодер-моделей | «Вопрос + контекст → ответ со ссылкой на статью» |
| **Классификатор типа вопроса** | `ruBERT-tiny` | Классификация (права, сроки, штрафы, порядок) | Небольшая разметка |

**Рекомендации по выбору:**
1. **Retriever:** дообучить `multilingual-e5-small` или MiniLM (подходит для CPU/слабой GPU). Сравнить «до / после» на тестовом наборе — это ядро экспериментальной части.
2. **Реранкер:** cross-encoder на базе `ruBERT-tiny`/`ruBERT-base`.
3. **Ответ:** extractive QA на `ruBERT` как основной вариант (нет галлюцинаций, ответ привязан к источнику); `ruT5` или LoRA-LLM — как сравнительный эксперимент.

**Практика дообучения:**
- Железо: для `e5-small`, MiniLM, `ruBERT-tiny` хватает CPU или слабой GPU; для `ruBERT-base`, `ruT5`, LoRA — GPU (Kaggle/Colab).
- Экономия: LoRA/адаптеры, fp16, малый размер батча с накоплением градиента.
- Борьба с переобучением: early stopping по validation, деление данных **по законам**, фиксированный seed, 3+ запуска.
- Вариант «до»: та же модель без дообучения используется **только как baseline в таблице**, а не как часть итоговой системы.
- Не забыть указать в тексте диплома источник базового чекпоинта, лицензию и что именно было дообучено.

## 1. Общая архитектура

```
Текст нормативного акта
   │
   ▼
[Парсинг структуры]  глава → статья → часть → пункт  (+ метаданные)
   │
   ▼
[Чанкинг]  по структуре документа
   │
   ▼
[Индексация]  BM25 / TF-IDF / LSA / свои эмбеддинги / ANN-индекс
   │
   ▼
[Поиск]  query → top-N кандидатов → гибридное слияние → переранжирование
   │
   ▼
[Ответ]  extractive (выделение фрагмента) / шаблонный / малый seq2seq
   │
   ▼
Ответ + ссылка на статью (источник)
```

## 2. Данные (основа всего проекта)

Без данных ни одна обучаемая модель не заработает. Это самое узкое место, поэтому описано подробно.

### 2.1 Корпус текстов
- Открытые источники: pravo.gov.ru, официальные публикации федеральных законов, кодексы (ГК, ТК, УК и др.), постановления.
- Желательно **1–5 млн слов**: для обучения эмбеддингов с нуля этого минимум.
- Сохранять структуру (статьи, пункты) и метаданные (закон, номер статьи).

### 2.2 Данные для поиска (вопрос → релевантная статья)
Аналогов готовых датасетов для вашей задачи нет, поэтому набор строится самостоятельно:
1. **Шаблонные вопросы** по структуре закона: «Что регулирует статья N?», «Какие права предоставляет …?», «В каком порядке …?». Генерация по названию статьи и ключевым фразам.
2. **Заголовок статьи → тело статьи**: естественные пары «запрос – документ».
3. **Inverse Cloze Task (ICT)**: случайное предложение из статьи берётся как псевдо-вопрос, остальное — как документ. Не требует ручной разметки.
4. **Ручная разметка контрольной выборки**: 100–300 вопросов с указанием релевантных статей. Обязательна: именно на ней считаются итоговые метрики.
5. **Разделение**: train / validation / test **по законам**, а не по случайным фрагментам. Иначе будет утечка данных.

## 3. Парсинг структуры нормативных актов

Конечный автомат или набор регулярных выражений по иерархии российских НПА:

```
Раздел  →  Глава  →  Статья  →  Часть  →  Пункт  →  Подпункт
```

| Элемент | Типичный шаблон |
|---|---|
| Глава | `^Глава\s+\d+[\.\-]?\d*\.?\s+.+` |
| Статья | `^Статья\s+\d+([\.\-]\d+)?\.\s+.+` |
| Часть | `^\d+\.\s+` |
| Пункт | `^\d+\)\s+` |
| Подпункт | `^[а-я]\)\s+` |

Результат парсинга — дерево с метаданными `{закон, глава, статья, часть, пункт}`.
Дополнительно: извлечение перекрёстных ссылок («в соответствии со статьёй 12 настоящего Закона») для построения графа связей.

## 4. Чанкинг

| Стратегия | Описание | Комментарий |
|---|---|---|
| Фиксированный размер | N символов/слов с перекрытием | Текущая реализация в проекте, baseline |
| По предложениям | Группировка предложений до лимита | Не разрывает мысль |
| **По структуре** | Один чанк = статья/часть/пункт | **Основной вариант для НПА** |
| Иерархический | Пункт + заголовок статьи + название закона в префиксе | Сохраняет контекст |
| Скользящее окно по структуре | Длинные статьи делятся по частям с перекрытием | Компромисс |
| Семантический | Разрез по резкому падению косинусной близости соседних предложений | Использует собственные эмбеддинги |

Для сравнения варьировать размер чанка (200 / 500 / 1000 символов) и перекрытие.

## 5. Поиск (Retrieval)

Основа проекта, поскольку текущий код уже реализует этот этап.

### 5.1 Предобработка русского текста
- Токенизация (регулярные выражения), приведение к нижнему регистру.
- **Нормализация слов**: собственный стеммер (алгоритм Портера для русского, реализуется вручную) либо словарная лемматизация, построенная по корпусу.
- Удаление стоп-слов (список строится по частотам корпуса).
- Нормализация номеров статей и юридических сокращений (ст., п., ч., ФЗ, РФ, ГК).

### 5.2 Разреженные (лексические) методы — реализуются вручную
| Метод | Суть |
|---|---|
| **TF-IDF** | Вес терма = частота × обратная частота документа, косинусная близость |
| **BM25 / BM25+** | Улучшенный TF-IDF с насыщением по частоте и нормировкой по длине. Параметры `k1`, `b` настраиваются на validation |
| **BM25F** | Разные веса для заголовка и тела статьи |
| **Символьные n-граммы** | Устойчивы к опечаткам и морфологическим вариантам |
| **Расширение запроса** | Псевдорелевантная обратная связь (RM3): уточнение запроса термами из топ-k |

### 5.3 Плотные (векторные) методы, обучаемые с нуля

| № | Подход | Описание |
|---|---|---|
| 1 | **LSA / LSI** | Матрица терм-документ → SVD → низкоразмерные векторы. Без нейросетей, быстро, хороший baseline |
| 2 | **Word2Vec с нуля** | Skip-gram с отрицательным сэмплированием на вашем корпусе. Вектор документа = взвешенное среднее векторов слов (с весами IDF) |
| 3 | **fastText-подобные** | Слово = сумма векторов символьных n-грамм. Хорошо работает для русской морфологии и опечаток |
| 4 | **GloVe с нуля** | Факторизация матрицы совстречаемости |
| 5 | **Dual-encoder (двухбашенная модель) с нуля** | Две небольшие сети (BiLSTM или малый Transformer) кодируют запрос и документ. Контрастное обучение (InfoNCE / in-batch negatives) на парах из раздела 2.2 |
| 6 | **Hard negatives** | Добавление в обучение «сложных» отрицательных примеров из BM25 |

> Реалистично: эмбеддинги с нуля на небольшом корпусе обычно **уступают BM25**. Это нормальный научный результат, который стоит честно показать и объяснить.
> Выигрыш даёт **гибрид** (см. 5.5).

### 5.4 Индексация (ANN)
| Метод | Реализация |
|---|---|
| **Brute force** | Матричное произведение, точный поиск. Достаточно для тысяч–десятков тысяч чанков |
| **LSH** (локально-чувствительное хеширование) | Случайные гиперплоскости, собственная реализация |
| **IVF** | K-means для центроидов, поиск в ближайших кластерах (собственная реализация k-means) |
| **Product Quantization** | Сжатие векторов, для расширенного эксперимента |
| **HNSW** | Граф малого мира. Сложнее, но реализуем |

Сравнивать по скорости и потере точности относительно точного поиска.

### 5.5 Гибридный поиск и слияние
- **RRF** (Reciprocal Rank Fusion): `score(d) = Σ 1 / (k + rank_i(d))`, `k ≈ 60`.
- Линейная комбинация нормированных оценок: `α · BM25 + (1 − α) · dense`, `α` подбирается на validation.
- Слияние по нескольким представлениям (слова, символьные n-граммы, LSA).

### 5.6 Переранжирование (Re-ranking)
| Подход | Описание |
|---|---|
| **Learning to Rank** на признаках | Признаки: BM25, косинус LSA, доля совпавших термов, совпадение номера статьи, длина, позиция. Модель: логистическая регрессия, градиентный бустинг (собственная реализация деревьев — опционально), pairwise RankNet/LambdaRank на PyTorch |
| Малый cross-encoder с нуля | Трансформер или BiLSTM-интеракция «запрос ⊕ документ» → оценка. Требует много данных |
| Правила | Бонус за точное совпадение номера статьи/термина из запроса |

## 6. Формирование ответа (Generation)

Без готовых языковых моделей полноценная генерация невозможна. Однако для юридической задачи есть **более подходящие и даже более надёжные** подходы.

| № | Подход | Идея | Плюсы |
|---|---|---|---|
| 1 | **Поиск фрагмента-ответа** (retrieval-based) | Ответ = найденная статья/пункт с цитатой и ссылкой | Полная достоверность, нет галлюцинаций |
| 2 | **Extractive QA: выбор предложений** | Оценка каждого предложения (BM25 + признаки + обученный классификатор), вывод top-1/2 | Просто, контролируемо |
| 3 | **Extractive QA: span-prediction с нуля** | BiLSTM/Transformer с вниманием «вопрос–контекст» (в духе BiDAF), предсказывает начало и конец ответа | Классический обучаемый подход, воспроизводим |
| 4 | **Шаблонные ответы** | Классификация типа вопроса (права, сроки, штрафы, порядок) + шаблон с подстановкой найденных фрагментов | Для типовых вопросов |
| 5 | **Малый seq2seq с нуля** | LSTM/Transformer encoder-decoder с механизмом копирования (**pointer-generator**) | Генерация «в стиле», но качество скромное |
| 6 | **Саммаризация извлечением** | TextRank (граф предложений) | Без обучения, реализуется вручную |

**Рекомендация:** 1 + 2 как основа, 3 как обучаемый компонент (содержательная часть диплома), 5 как опциональный эксперимент для сравнения.

Обязательно в ответе: **номер статьи, название закона, цитата-источник**. Если уверенность низкая (порог по оценке), система отвечает «в базе нет релевантной информации».

## 7. Оценка и эксперименты

### 7.1 Метрики
| Этап | Метрики |
|---|---|
| Retrieval | Recall@k, Precision@k, MRR, nDCG@k, Hit Rate |
| Извлечение ответа | Exact Match, F1 по токенам, точность ссылки на статью |
| Скорость/память | время индексации, время запроса, размер индекса |
| Система целиком | доля вопросов с правильной статьёй в топ-k |

### 7.2 План экспериментов (основа глав диплома)
1. **Retrieval:** TF-IDF → BM25 → LSA → Word2Vec/fastText → dual-encoder → гибрид.
2. **Чанкинг:** фиксированный vs. по структуре; размеры и перекрытие.
3. **Устойчивость:** символьные n-граммы vs. словные при опечатках в запросах.
4. **ANN:** brute force vs. LSH vs. IVF (скорость/точность).
5. **Реранкер:** с признаками vs. без.
6. **Ответ:** выбор предложений vs. span-prediction vs. шаблоны.
7. **Абляции:** вклад каждого модуля в итоговое качество.

### 7.3 Методика
- Фиксировать seed, повторять обучение 3+ раза, указывать среднее и разброс.
- Делить данные по законам. Тестовая выборка не используется при подборе гиперпараметров.
- Для сравнения — парный bootstrap или тест Уилкоксона для значимости различий.

- Создан **набор данных** (вопросы для retrieval).
- Проведено **сравнительное исследование** подходов.

## 11. Риски и ограничения

| Риск | Что делать |
|---|---|
| Мало данных для нейросетей с нуля | Сильный классический baseline (BM25), дообучение вместо обучения с нуля и честный анализ |
| Эмбеддинги с нуля слабее BM25 | Показать это как результат; продемонстрировать выигрыш гибрида |
| Нет готовых датасетов вопросов | Шаблоны + ICT + ручная контрольная выборка |
| Нехватка вычислительных ресурсов | Малые модели (1–5 млн параметров), кластеры Kaggle/Colab |
| Утечка данных между train и test | Делить по законам, а не по фрагментам |
| Нечестная оценка | Ручная разметка контрольных вопросов; не строить ground truth по совпадению слов |
